<a name="diagnostico-em-30-segundos"></a>

## 🧭 Diagnóstico en 30 segundos

```bash
docker compose ps                                               # ¿los tres contenedores están 'running' y 'healthy'?
docker compose logs --tail 50 ftp                               # ¿qué dijeron el entrypoint y el pure-ftpd?
docker compose logs --tail 50 painel                            # ¿y el panel?
docker compose logs --tail 50 nginx                             # ¿y el nginx, que queda delante del panel?
```

**Resultado esperado:** los tres contenedores (`allsafe-ftp`, `allsafe-ftp-painel` y `allsafe-ftp-nginx`) `running` y `healthy` y, en el log, las líneas `FTP pronto em 2121/tcp; ...`, `Painel pronto no soquete /nginx/painel.sock, atrás do nginx; ...` y `nginx pronto em 8443/tcp (HTTPS), à frente do painel; ...`. Cualquier otra cosa apunta a una de las tablas de abajo.

Los tres entrypoints abortan con `FALHA: <motivo>` y el contenedor se reinicia en bucle: el motivo está siempre en el primer intento del log.

<a name="o-container-nao-sobe"></a>

## ❌ El contenedor no arranca

| Mensaje en el log | Causa | Cómo verificar | Corrección |
|---|---|---|---|
| `ERRO: porta já em uso por outro programa: <IP>:<porta>` (en el `deploy.sh`) | Otro programa del host ya escucha en el puerto del FTP, del panel o del rango pasivo | `ss -ltnp` | Cambie `FTP_PORT`, `PAINEL_PORT` o el rango pasivo en el `.env`, o detenga el otro programa, y ejecute `./deploy.sh` de nuevo |
| `ERRO: não foi possível criar as pastas em <DATA_DIR>` (en el `deploy.sh`) | Quien ejecuta el `deploy.sh` no puede escribir en la carpeta superior de `DATA_DIR` (por defecto, `/srv`, donde solo root escribe). No se construyó ni se levantó nada | `ls -ld /srv /srv/allsafe-ftp-stack` | Cree la carpeta una vez para su usuario, con el comando que el mensaje muestra (`sudo install -d -o <usuário> /srv/allsafe-ftp-stack`), o apunte `DATA_DIR`, `BACKUP_DIR` y `TEMP_DIR` a otro lugar en el `.env`: [Configuración](configuracion.md#pastas-e-nomes). Después, `./deploy.sh` de nuevo |
| `ERRO: os containers não ficaram healthy` (en el `deploy.sh`) | Uno de los contenedores se detuvo o no respondió en el plazo (180 s más un cuarto de segundo por puerto pasivo) | `docker compose logs --tail 50 ftp painel nginx` | Corrija la causa mostrada en el log (las filas de abajo cubren las más comunes) y ejecute `./deploy.sh` de nuevo |
| `ERRO: o perfil '…' pede … CPUs (FTP_CPU_LIMIT) e este servidor tem …` (o `de memória (FTP_MEMORY_LIMIT)`), en el `deploy.sh` | El perfil elegido es mayor que el servidor. No se modificó nada | `nproc` y `free -m` | Use un perfil menor con `--size`: [Perfiles](perfiles.md#o-servidor-aguenta) |
| `ERRO: FTP_TLS_MODE deve ser 0 (sem TLS), 1 (opcional), 2 (obrigatório no login) ou 3 (…)` (en el `deploy.sh`) | Valor fuera de `0` a `3` en el `.env`. No se modificó nada | `grep '^FTP_TLS_MODE=' .env` | Use `2`, el valor por defecto: [Configuración](configuracion.md#tls) |
| `ERRO: Docker não encontrado`, `ERRO: plugin Docker Compose não encontrado` o `ERRO: sem acesso ao Docker` (en el `deploy.sh`) | Docker detenido, sin permiso para el usuario, o sin el plugin Compose | `docker info` y `docker compose version` | Inicie Docker, entre en el grupo `docker` o instale el plugin Compose v2 |
| `ERRO: ... não é uma chave age válida` (en el `deploy.sh`) | `.secrets/backup-chave-privada.txt` fue modificado o cambiado por otro archivo. No se modificó nada en él | `ls -l .secrets/backup-chave-*.txt` | Guarde de nuevo la clave conservada en el gestor de contraseñas. Sin ella, las copias hechas antes no se abren: para empezar un par nuevo, borre los dos archivos y ejecute `./deploy.sh`. Vea [Copia de seguridad y restauración](backup.md#chave) |
| `FALHA: segredo /run/secrets/ftp_usuario_inicial_senha ausente` | `.secrets/ftp-usuario-inicial-senha.txt` no existe | `ls -l .secrets/` | Ejecute `./deploy.sh`, que crea el archivo con una contraseña fuerte. Vea [Secretos](secretos.md) |
| `FALHA: FTP_BIND_IP=… não é IP privado` (o `FTP_PASSIVE_IP`) | Dirección fuera de `127/8`, `10/8`, `172.16/12` y `192.168/16`; el contenedor se reinicia en bucle | `grep -E "FTP_(BIND\|PASSIVE)_IP" .env` | Use la IP **interna** del servidor. La stack no acepta `0.0.0.0` ni, por defecto, IP pública: vea [Seguridad](seguridad.md#rede-privada) |
| `FALHA: REDE_PERMITIR_IP_PUBLICO deve ser 'nao' ou 'sim'; está '…'` (en el `deploy.sh` y en los tres contenedores) | La opción de IP pública tiene otro valor, como `true` o `1` | `grep '^REDE_PERMITIR_IP_PUBLICO=' .env` | Use `nao`, el valor por defecto. `sim` solo después de leer la alerta: [Seguridad](seguridad.md#ip-publico) |
| `FALHA: REDE_IPV6 deve ser 'nao' ou 'sim'; está '…'` (en el `deploy.sh` y en los tres contenedores) | La opción de IPv6 tiene otro valor, como `true` o `1` | `grep '^REDE_IPV6=' .env` | Use `nao`, el valor por defecto, o `sim`: [Configuración](configuracion.md#ipv6) |
| `FALHA: FTP_BIND_IPV6=… não é IPv6 privado` (o `PAINEL_BIND_IPV6`) | Dirección fuera de `::1` y del rango local único (`fc00::/7`), o escrita con corchetes o con zona (`%eth0`) | `grep -E '^(FTP\|PAINEL)_BIND_IPV6=' .env` | Use `::1` o una dirección del rango local único, sin corchetes. `::` nunca se acepta; IPv6 pública, solo con la opción de IP pública: [Seguridad](seguridad.md#ip-publico) |
| `FALHA: FTP_SUBNET_IPV6=… não serve` | La subred IPv6 de los contenedores no es un rango local único con prefijo `/64`, o tiene bits de máquina | `grep '^FTP_SUBNET_IPV6=' .env` | Use una red como `fd29:1::/64`: [Configuración](configuracion.md#ipv6) |
| `ERRO: REDE_IPV6=sim, mas PAINEL_REDES_PERMITIDAS não tem nenhuma rede IPv6` (en el `deploy.sh`) | Con el IPv6 activado y solo redes IPv4 en la lista, el nginx rechazaría a todo cliente del panel en IPv6 | `grep '^PAINEL_REDES_PERMITIDAS=' .env` | Añada la red IPv6 **privada** de quien administra. Para abrir desde el propio servidor, en `https://[::1]:8443`, la red es la de `FTP_SUBNET_IPV6` |
| `ERRO: REDE_IPV6=sim, mas o IPv6 está desligado no kernel deste servidor` (en el `deploy.sh`) | El sistema del servidor tiene el IPv6 desactivado | `cat /proc/sys/net/ipv6/conf/all/disable_ipv6` responde `1`, o el archivo no existe | Active el IPv6 en el servidor, o vuelva a `REDE_IPV6=nao` |
| `ERRO: REDE_IPV6=sim pede Docker 27 ou mais novo` (en el `deploy.sh`) | Docker antiguo, que no da IPv6 a la red de los contenedores sin un cambio en la configuración del servicio | `docker version --format '{{.Server.Version}}'` | Actualice Docker, o vuelva a `REDE_IPV6=nao` |
| `ERRO: a rede … não ficou com o IPv6 pedido em REDE_IPV6` (en el `deploy.sh`) | La red de los contenedores ya existía y no se rehízo con el cambio | `docker network inspect -f '{{.EnableIPv6}}' allsafe-ftp-network` | `./deploy.sh --remover` y después `./deploy.sh`; los datos se conservan |
| `FALHA: …=… não é um endereço IPv4 de servidor` o `não é uma rede IPv4 aceita` | Con `REDE_PERMITIR_IP_PUBLICO=sim`, el valor es `0.0.0.0`, multicast, reservado o una red más amplia que `/8` | `grep -E '^(FTP_BIND_IP\|FTP_PASSIVE_IP\|PAINEL_BIND_IP\|PAINEL_REDES_PERMITIDAS\|PAINEL_CERT_CN)=' .env` | Indique la dirección y las redes una a una; "todos" no se acepta ni con la opción activada |
| `REDE_PERMITIR_IP_PUBLICO=sim exige FTP_TLS_MODE=2 ou 3` (en el `deploy.sh` y en el contenedor del FTP) | La opción de IP pública está activada con el FTP sin TLS o con TLS opcional | `grep -E '^(REDE_PERMITIR_IP_PUBLICO\|FTP_TLS_MODE)=' .env` | Vuelva `FTP_TLS_MODE` a `2` o desactive la opción. Equipo sin TLS solo en red interna: [Seguridad](seguridad.md#ftp-sem-tls) |
| `FTP_TLS_EXCECOES deve ser …` (en el `deploy.sh` y en los contenedores del FTP y del panel) | La excepción de TLS por usuario tiene un valor distinto de `nao` y de `sim`. No se modificó nada | `grep '^FTP_TLS_EXCECOES=' .env` | Use `sim`, el valor por defecto, o `nao`: [Configuración](configuracion.md#tls) |
| `TLS por usuário sem efeito: só vale com FTP_TLS_MODE=2` (en el `deploy.sh` y en el log del FTP), y el panel sin la columna **TLS** | El TLS del FTP está en `0`, `1` o `3`: la dispensa por usuario solo existe sobre el modo `2`. Es un aviso, y la instalación arranca | `grep -E '^FTP_TLS_(EXCECOES\|MODE)=' .env` | Para dispensar solo un equipo, vuelva `FTP_TLS_MODE` a `2` y ejecute `./deploy.sh`: [Seguridad](seguridad.md#tls-por-usuario) |
| `TLS por usuário sem efeito: não vale com REDE_PERMITIR_IP_PUBLICO=sim` (en el `deploy.sh` y en el log del FTP), y el panel sin la columna **TLS** | El servidor acepta dirección pública: nadie queda dispensado del TLS, aunque esté en la lista. Es un aviso, y la instalación arranca | `grep -E '^(FTP_TLS_EXCECOES\|REDE_PERMITIR_IP_PUBLICO)=' .env` | Equipo sin TLS solo en red interna: [Seguridad](seguridad.md#tls-por-usuario) |
| `FALHA: o pure-authd saiu: o container encerra para ninguém entrar sem a conferência do porteiro` (o `o vigia saiu`, `o pure-ftpd saiu`, o `o observador da lista do TLS saiu`), y el `allsafe-ftp` se reinicia | Uno de los procesos del FTP se detuvo. El contenedor termina a propósito y Docker lo levanta de nuevo | `docker compose logs --tail 50 ftp`; `docker inspect -f '{{.RestartCount}}' allsafe-ftp` | Una sola vez, nada que hacer: el FTP vuelve por sí solo en segundos. Si se repite, recoja los registros: [Herramientas de validación](#ferramentas-de-validacao) |
| `FALHA: o pure-authd não abriu o soquete /run/pure-authd.sock: o FTP não sobe sem o porteiro` o `FALHA: o vigia não abriu o soquete /dev/log: o FTP não sobe sem a contagem das senhas erradas` | El proceso que verifica los bloqueos y el TLS por usuario, o el que cuenta las contraseñas incorrectas, no se inició | `docker compose logs --tail 50 ftp` | Ejecute `./deploy.sh` de nuevo. Si continúa, recoja los registros: [Herramientas de validación](#ferramentas-de-validacao) |
| `FALHA: FTP_BLOQUEIO_TENTATIVAS deve ficar entre 0 e 100 (0 desliga o bloqueio por tentativa)` o `FALHA: FTP_BLOQUEIO_MINUTOS deve ficar entre 1 e 1440` (en los contenedores del FTP y del panel) | El valor por defecto del bloqueo por intento está fuera del rango o no es un número | `grep '^FTP_BLOQUEIO_' .env` | Corrija en el `.env` y ejecute `./deploy.sh`. El valor por defecto es `5` y `15`: [Configuración](configuracion.md#limites-de-sessao) |
| `FALHA: /auth/bloqueios é link simbólico: remova-o` | La carpeta de los bloqueos en `DATA_DIR/auth` fue cambiada por un enlace | `ls -ld "$DATA_DIR/auth/bloqueios"` | Borre el enlace y ejecute `./deploy.sh`: la carpeta se crea de nuevo vacía |
| `FALHA: BLOQUEIO_ENDERECO_ERROS deve ficar entre 0 e 100 (0 desliga o bloqueio por endereço)`, `FALHA: BLOQUEIO_ENDERECO_HORAS deve ficar entre 1 e 720` o `FALHA: BLOQUEIO_ENDERECO_DIAS deve ficar entre 1 e 3650` (en el `deploy.sh` y en los contenedores del FTP y del panel) | La regla del bloqueo por dirección está fuera del rango o no es un número. No se modificó nada | `grep '^BLOQUEIO_ENDERECO_' .env` | Corrija en el `.env` y ejecute `./deploy.sh`. El valor por defecto es `5`, `24` y `120`: [Configuración](configuracion.md) |
| `FALHA: /auth/enderecos é link simbólico: remova-o` | La carpeta de los bloqueos por dirección en `DATA_DIR/auth` fue cambiada por un enlace | `ls -ld "$DATA_DIR/auth/enderecos"` | Borre el enlace y ejecute `./deploy.sh`: la carpeta se crea de nuevo vacía |
| `defina FTP_PASSIVE_IP no .env` (en cualquier comando que llama a Compose) | `.env` de una instalación anterior a la `0.17.0`, todavía con `FTP_PUBLIC_IP` | `grep -E "^FTP_(PUBLIC\|PASSIVE)_IP=" .env` | Ejecute `./deploy.sh`: cambia el nombre por sí solo, mantiene el valor y guarda el `.env` anterior en `BACKUP_DIR`. Vea [Configuración](configuracion.md#ftp-passive-ip) |
| `ERRO: .env ainda traz FTP_PASSWORD` (en el `deploy.sh`) | `.env` de una versión anterior, con contraseña | `grep -c "^FTP_PASSWORD" .env` | Guarde la contraseña en `.secrets/ftp-usuario-inicial-senha.txt` (`chmod 600`) y borre `FTP_PASSWORD` y `FTP_PASSWORD_FILE` del `.env` |
| `bind source path does not exist` al arrancar | Carpeta de `DATA_DIR` ausente (Compose no la crea) | `ls "$DATA_DIR"` | Ejecute `./deploy.sh`, que crea `dados/`, `auth/`, `certs/`, `painel/` y `nginx/` |
| `allsafe-ftp` en `unhealthy`, con el contenedor en ejecución y sin `FALHA` en el log | El `pure-ftpd` está vivo, pero no responde en el puerto de control. Docker solo lo señala: no reinicia el contenedor por sí solo | `docker compose exec ftp /usr/local/sbin/allsafe-ftp-saude; echo $?` (`0` = atendiendo) | `docker compose restart ftp`. Si vuelve a ocurrir, recoja los registros: [Herramientas de validación](#ferramentas-de-validacao) |
| `FALHA: a senha FTP deve ter pelo menos 12 caracteres` | Contraseña corta, o archivo vacío o solo con una línea en blanco | `wc -c .secrets/ftp-usuario-inicial-senha.txt` | Guárdela de nuevo: `printf '%s' 'clave-con-12+-caracteres' > .secrets/ftp-usuario-inicial-senha.txt` |
| `FALHA: FTP_USER invalido` | Nombre fuera de `^[a-z_][a-z0-9_-]{0,31}$` | `grep '^FTP_USER=' .env` | Use minúsculas, sin espacio ni tilde; comience con letra o `_` |
| `FALHA: faixa passiva invalida` o `fora dos limites` | `FTP_PASSIVE_PORT_START` o `FTP_PASSIVE_PORT_END` no numéricos, por debajo de `1024`, por encima de `65535` o invertidos | `grep PASSIVE .env profiles/*.env` | Corrija en el `.env`; mantenga el inicio menor o igual al fin |
| `FALHA: FTP_TLS_MODE deve ser 0, 1, 2 ou 3` | Valor no válido | `grep '^FTP_TLS_MODE=' .env` | Use `2`, el valor por defecto. `0` y `1` son solo para equipos sin TLS: [Configuración](configuracion.md#tls) |
| `bind: address already in use` | `FTP_PORT` o el rango pasivo ya están ocupados en el host | `ss -ltnp` | Cambie el puerto o el rango, o libere a quien lo está usando |
| `bind: cannot assign requested address` | `FTP_BIND_IP` no existe en el host | `ip -br addr` | Ajuste a una IP configurada en la máquina |

<a name="conecta-mas-falha-no-login-ou-na-listagem"></a>

## 🔌 Conecta pero falla en el login o en el listado

| Síntoma | Causa probable | Cómo verificar | Corrección |
|---|---|---|---|
| El cliente conecta y se cae cuando se le exige el `AUTH TLS` | Cliente usando FTP **puro** o FTPS **implícito** (puerto 990) | Configuración del cliente; log del contenedor | Configure el cliente para **FTP explícito sobre TLS** en el puerto de control. Si el equipo no tiene TLS: [Equipo antiguo](#ftp-sem-tls) |
| El cliente pide TLS y el servidor rechaza el `AUTH TLS` | El servidor está en `FTP_TLS_MODE=0`, sin TLS | `grep '^FTP_TLS_MODE=' .env`; el `AVISO` al final del `./deploy.sh` | Vuelva a `FTP_TLS_MODE=2` y ejecute `./deploy.sh`, o use el modo `1` si hay equipos antiguos en el mismo servidor |
| `530 Login authentication failed` | Contraseña incorrecta, el usuario no existe en la PureDB o UID por debajo de 10000 | `./manage-user.sh list` | Cree de nuevo la contraseña con `./manage-user.sh passwd <usuario>` |
| `530 Login authentication failed` con la contraseña correcta, solo a ciertas horas, después de unos 5 segundos de espera | El usuario tiene horario propio y la entrada se intentó fuera de él. El servidor responde como responde a la contraseña incorrecta | `./manage-user.sh limites <usuario>` muestra `horario=`; `docker compose exec ftp date` muestra la hora que usa el servidor | Ajuste o quite el horario en **Editar**, en la pestaña Usuarios, o con `./manage-user.sh limites <usuario> horario=`: [Panel web](panel.md#limites) |
| `530 Login authentication failed` con la contraseña correcta, a cualquier hora, solo desde una dirección | Esa dirección falló la contraseña del usuario demasiadas veces y está bloqueada para él. Hasta el fin del plazo, ni la contraseña correcta entra desde allí | `./manage-user.sh bloqueios <usuario>`; en el panel, la marca **bloqueado** junto al nombre | Corrija la contraseña en el equipo y quite el bloqueo: **Editar** ➜ **Desbloquear**, en la pestaña Usuarios, o `./manage-user.sh desbloquear <usuario>`. Sin eso, sale por sí solo al fin del plazo: [Seguridad](seguridad.md#bloqueio-por-tentativa) |
| `530 Login authentication failed` con la contraseña correcta, para todos los usuarios que llegan desde una dirección | La dirección superó el límite de errores de usuario y contraseña, o fue bloqueada por el administrador, sola o dentro de un prefijo, y tiene el bloqueo por dirección: no entra en el FTP ni en el panel, con ninguna cuenta | `./manage-user.sh enderecos`; en el panel, la pestaña Bloqueos; `docker compose logs ftp \| grep 'bloqueio do endereço'` | Corrija la contraseña en el equipo que fallaba y libere la dirección: **Desbloquear**, en la pestaña Bloqueos, o `./manage-user.sh endereco-liberar <endereco ou prefixo>`, con lo que aparece en `origem=` en la lista. Con varios equipos detrás de la misma dirección, revise el límite: [Seguridad](seguridad.md#bloqueio-por-endereco) |
| El usuario vuelve a quedar bloqueado poco después de desbloqueado | El equipo sigue con la contraseña incorrecta guardada e intenta por sí solo, u otro equipo usa el mismo usuario desde la misma dirección con la contraseña antigua | `docker compose logs ftp \| grep 'vigia: entrada recusada'` muestra el usuario y la dirección de cada contraseña incorrecta | Corrija la contraseña en todo equipo que usa ese usuario, y después desbloquee. Dé a cada equipo su propio usuario |
| `530 Login authentication failed` sin TLS, con la contraseña correcta | El usuario no está dispensado del TLS, y otro sí. La contraseña pasó en texto plano | `./manage-user.sh tls-lista`; `docker compose logs ftp \| grep porteiro` | Configure el equipo para TLS y cambie la contraseña. Si no habla TLS, dispense al usuario en la pestaña Usuarios del panel o con `./manage-user.sh tls-dispensar <usuario>`: [Seguridad](seguridad.md#tls-por-usuario) |
| El usuario dispensado del TLS sigue sin entrar sin TLS (`421` o tiempo agotado) | El TLS por usuario está sin efecto: `FTP_TLS_EXCECOES=nao`, `FTP_TLS_MODE` distinto de `2` o `REDE_PERMITIR_IP_PUBLICO=sim`. La lista de los dispensados queda guardada y no vale | Pestaña Seguridad del panel, fila **TLS del FTP**; `./deploy.sh --check-only` | Deje `FTP_TLS_EXCECOES=sim` y `FTP_TLS_MODE=2` y ejecute `./deploy.sh`. Una instalación anterior a la `0.45.0` trae `FTP_TLS_EXCECOES=nao` guardado en el `.env` |
| Login OK, `LIST` o `STOR` se cuelga y da timeout | Modo **activo**, o rango pasivo o `FTP_PASSIVE_IP` bloqueados o incorrectos | `docker compose ps` muestra el rango publicado; pruebe el puerto `30000/tcp` desde el cliente | Use el modo **pasivo**; libere en el firewall el rango pasivo del perfil (`30000-30099/tcp` en el `small`); `FTP_PASSIVE_IP` con la IP que el cliente alcanza |
| `425 Could not open data connection` | `FTP_PASSIVE_IP` apunta a una IP que el cliente no alcanza | `grep '^FTP_PASSIVE_IP=' .env` | Defina `FTP_PASSIVE_IP` con la IP que el cliente alcanza y libere el rango pasivo hasta él. Por defecto la stack solo acepta IP privada |
| Error de certificado en el cliente | El certificado todavía es el autofirmado | `openssl s_client -connect TU_IP:21 -starttls ftp` muestra el emisor | Instale un certificado real ([Operación](operacion.md#certificado-real-de-producao)) o, solo en prueba, desactive la verificación en el cliente |

<a name="ftp-sem-tls"></a>

### Equipo antiguo que no habla TLS

El síntoma es siempre el mismo: el equipo conecta en el puerto de control y la sesión se cae antes del login. Por defecto (`FTP_TLS_MODE=2`), el servidor rechaza a quien no pide TLS. Confirme simulando el equipo, sin TLS:

```bash
curl -v --max-time 10 --user backup-olt ftp://TU_IP:21/
```

**Resultado esperado**, con el servidor en el valor por defecto: `421-Sorry, cleartext sessions and weak ciphers are not accepted on this server.` y el `curl` desistiendo enseguida. Es el servidor funcionando como debe.

Si el equipo realmente no tiene cómo hablar TLS (revise el manual y la versión del firmware antes), hay dos caminos. El primero es dispensar del TLS solo a su usuario, en la pestaña Usuarios del panel, con la casilla **Equipo sin soporte de TLS** al crearlo o con el botón **Dispensar del TLS** después: los demás siguen obligados. El segundo son los modos `FTP_TLS_MODE=1` (opcional) y `FTP_TLS_MODE=0` (sin TLS), que valen para todos. En cualquiera de ellos, quien entra sin TLS envía contraseña y archivo en **texto plano**: lea las condiciones en [Seguridad](seguridad.md#ftp-sem-tls) antes de activar.

Mientras haya algún usuario dispensado, la misma prueba cambia de respuesta: el servidor pide la contraseña y responde `530 Login authentication failed` al usuario que no está dispensado, incluso con la contraseña correcta.

## ☁️ Destinos: S3, rclone y bot de Telegram

Cuando una prueba, un envío por el botón o una pasada no sale bien, el panel dice el motivo en una frase: en el aviso de la pantalla, en la tarjeta del destino (**La última pasada se detuvo antes del final**) y en la pestaña Log. La situación de cada destino y la última pasada salen también por la terminal, sin ningún secreto. La salida de este comando está en portugués:

```bash
docker compose exec painel python3 /opt/painel/servidor.py --destinos
```

**Resultado esperado:** una línea por destino: `não configurado` (no configurado), o `ligado` (activado) o `desligado` (desactivado) con la carpeta, el intervalo y la última pasada. Con `--copia` en lugar de `--destinos`, sale la situación de la [copia del sistema a S3](panel.md#copia-do-sistema) y la última copia.

| El panel dice | Causa | Cómo verificar | Corrección |
|---|---|---|---|
| `el nombre de la dirección no fue encontrado` | El nombre del servicio no se resuelve desde dentro del contenedor del panel | `docker compose exec painel getent hosts <nome>` | Corrija la **Dirección del servicio**, o el DNS del servidor |
| `la dirección no es aceptada por el panel, o el servicio envió la solicitud a otra dirección` | El nombre lleva a una dirección que el panel no alcanza (el propio contenedor, dirección de enlace, de grupo o reservada), o el S3 respondió con una redirección: bucket de otra región o dirección que no es la del servicio | La **Región** y la **Dirección del servicio** en el registro del bucket, en el servicio | En **Modificar**, guarde la región y la dirección del bucket |

| `los usuarios se estaban modificando y su lista no pudo leerse a tiempo` | Un usuario estaba siendo creado, modificado o eliminado, y el bloqueo de la lista no se soltó en 30 segundos | — | Solicite la copia de nuevo |
| `falta espacio en disco en el servidor para montar una parte de la copia` | Cada parte, ya cifrada, se monta en `DATA_DIR/painel` antes de salir, y el disco no tiene libres el tamaño de una parte más 64 MiB | `df -h` en la carpeta de `DATA_DIR` | Libere espacio. La parte tiene 16 MiB o más y crece con el disco en uso: cerca de 1 GiB por cada 9 TiB |
| `hay demasiadas carpetas, una dentro de otra, para que el panel las abra` | Un árbol de carpetas más profundo que el límite de archivos abiertos del contenedor | — | Reduzca la profundidad de las carpetas, o haga la copia con el `scripts/backup.sh` |
| `otra copia del sistema está en curso` | Se hizo clic en el botón, o se llamó a la terminal, con una copia en ejecución | La marca **en curso** en la tarjeta | Espere a que termine |
| `la copia se guardó en el destino, pero el archivo con su suma no: haga otra copia` | El servicio falló después de guardar la copia y antes de guardar el `.sha256` | Los objetos en la carpeta de la copia, en el bucket | Solicite otra copia. La que quedó sin el `.sha256` todavía se restaura, con el aviso `soma não conferida` |
| **La copia anterior fue interrumpida por el reinicio del panel** | El contenedor del panel se reinició, o la stack fue actualizada, en medio de la copia | `docker compose ps painel`, con el tiempo en marcha | Haga clic en **Copiar y enviar ahora**. El envío en partes que quedó sin terminar ocupa espacio en el bucket hasta deshacerse: ponga en el bucket la regla que expira el envío en partes incompleto |
| La rutina de la copia del sistema no se ejecutó | `0` días guardados (marca **solo por el botón**), la última copia tiene menos días que la rutina, el destino está sin los secretos, o la rutina fue guardada después de la hora de hoy: vale desde la siguiente hora marcada en adelante | La marca y las líneas **Rutina** y **Última copia** de la tarjeta; `docker compose exec painel python3 /opt/painel/servidor.py --copia` | En **Modificar**, en la tarjeta de la copia, guarde los días y la hora |
| El bot no envió en el acto un archivo que llegó | El archivo llegó con un nombre y fue renombrado o movido por FTP, fue copiado directo en el servidor, o el aviso de llegada no fue guardado: sin el aviso, vale la espera de dos minutos sin cambiar | La línea **Todavía llegando** en la tarjeta del bot | Nada que hacer: sale por sí solo después de la espera. Para enviarlo ya, use el botón **Telegram** en la fila del archivo |
| El bot no envió los archivos que ya estaban en la carpeta | El bot solo envía lo que llega después de ser activado | La línea **Última pasada** de la tarjeta | Envíe cada uno por el botón **Telegram** de la pestaña Archivos |
| La conversación recibió un aviso en lugar del archivo | El archivo supera el límite del bot | El tamaño en el aviso | El archivo sigue en el servidor: descárguelo por el panel |
| Los botones **Telegram**, **rclone** y **S3** no aparecen en la pestaña Archivos | El destino no fue guardado, está sin los secretos, o `PAINEL_DESTINOS=nao`. La pantalla Mis archivos, del usuario del FTP, nunca tiene esos botones | La pestaña Destinos; `grep '^PAINEL_DESTINOS=' .env` | Guarde el destino en la pestaña Destinos |
| La pestaña Destinos no está en el menú | `PAINEL_DESTINOS=nao`, o la sesión es de un usuario del FTP | `grep '^PAINEL_DESTINOS=' .env` | `PAINEL_DESTINOS=sim` y `./deploy.sh` |

## 🧪 Herramientas de validación

```bash
./scripts/validate.sh                     # bash -n de los scripts y compose config
./scripts/validate.sh --runtime           # también exige los tres servicios running y healthy
docker compose exec ftp /usr/local/sbin/allsafe-ftp-saude && echo atendendo   # lo que prueba el healthcheck
./tests/testar.sh                       # batería completa en una instancia de prueba separada
```

**Resultado esperado:** `Validacao FTP concluida.`, `atendendo` y `Bateria aprovada: nenhum desvio.` La batería no toca la instalación en uso; si pasa y su instalación falla, la diferencia está en el `.env`, en los datos o en la red del host. Vea [Scripts](scripts.md#testar).

¿Sigue atascado? Recoja y analice:

```bash
TEMP_DIR="$(sed -n 's/^TEMP_DIR=//p' .env | tail -n 1)"   # el TEMP_DIR de su .env
mkdir -p "$TEMP_DIR"
docker compose logs --no-color ftp painel nginx > "$TEMP_DIR/allsafe-ftp.log"
docker inspect allsafe-ftp allsafe-ftp-painel allsafe-ftp-nginx > "$TEMP_DIR/allsafe-ftp.inspect.json"
```

**Resultado esperado:** dos archivos en `TEMP_DIR` con el log completo y la configuración efectiva de los contenedores. Bórrelos al terminar.

> ⚠️ El `inspect` trae las variables de entorno del contenedor. Ninguna de ellas es contraseña (la contraseña solo existe en el secreto), pero el archivo muestra IP y rutas del host: revíselo antes de compartir.
